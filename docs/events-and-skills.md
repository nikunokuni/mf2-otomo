# 大会・修行・冒険・技のメモ

口頭でもらった仕様のメモ。**別ブランチと衝突しないように、既存ファイルは触らずこの1枚だけを追加している。**
まだ実装していない話が中心で、`docs/roadmap.md` の ② とは別の軸（イベントと技）をまとめたもの。

現状のコードとの関係だけ先に書いておく：

- 育成計画のセットは `{ ht, hc, lt, tc, mc, ac, weeks, items }`（`js/simulator/growth-calc.js` の `newSet()`）。
  **`tc`＝大会 / `mc`＝修行 / `ac`＝冒険 の回数**を持っているが、いまは
  **寿命（`EV_COST`）と暦（`EV_WEEKS`）を減らすだけ**で、パラメータは1も動かない。
- 暦の計算は `weekToDate(startMonth, startWeek, offset)`。**1か月＝4週**で、
  月 `= (floor(total/4) % 12) + 1`、週 `= (total % 4) + 1`。
  つまり「○月◎週」を指定するイベントは、すでにこの関数だけで判定できる形になっている。
- ヨイワルはモンスタータブに入力欄があるだけで、**計算には一切使っていない**（README にも明記ずみ）。
  技の習得条件を入れると、ここが初めて計算に効いてくる。

### 大会での伸び（未実装）

- 優勝すると **ランダムでステータスが上がる**。内部数値も少し動く。
- 上昇値は **育成段階では決まらない**。**大会のランクと大会の成績**で決まる。
  （トレーニングの上昇値が段階×成長適正で決まるのとは、まったく別のテーブル）
- **正確な上昇値は分かっていない。** 大量に試せば割り出せるかもしれないが、**調べるのは見送る。**
  代わりに **合計値の目安**を使う。

| ランク | 優勝したときの合計上昇値（目安） |
|---|---|
| D | 10 |
| B | 20 |
| S | 30 |

「合計」なので、**どのパラメータに何ぶん振られるかは分からない**（ランダム）。
アプリで扱うのも合計値までにする。

### 9回ぶんの合計（すべて優勝した場合）

| 大会 | ランク | 目安 |
|---|---|---|
| D公式戦 | D | 10 |
| B公式戦 | B | 20 |
| S公式戦 | S | 30 |
| 4大大会 ×4 | S（想定） | 30 × 4 = 120 |
| レジェンド杯 | 未確認 | － |
| シルバー杯 | 未確認 | － |
| **合計** | | **210 くらい** |

公式戦3回で60、4大大会で120。残る2つを合わせて30前後とみると **210くらい**になる。
（レジェンド杯とシルバー杯のランクは未確認。合計210は目安として置いておく）

育成計画の試算に210前後が乗るかどうかは大きいので、**ざっくりでも入れる価値はある**。

### 入れるとしたらどうなるか

**パラメータ別に振り分けない。合計値だけを足す。** これなら必要な入力はランクだけで済む。

- セットの `tc`（回数）は寿命と暦の計算にそのまま使い、**ランクの内訳を別に持つ**。

  ```
  set.tc    = 3                      // これまでどおり。寿命-4 / 暦+1週 ×3
  set.tRank = { D:1, B:1, S:1 }      // 追加。合計は tc と一致させる
  ```

  旧データには `tRank` が無いので、**無いときは上昇0**として読めば移行はいらない。
- 上昇値の目安は `js/data/growth.js` に `TOURN_GAIN = { D:10, B:20, S:30 }` として置く。
  段階の `HM/HS/LG` とは無関係なので混ぜない。
- 結果欄では **トレーニングぶんの確定値とは別の行**にして、
  「大会ぶん **+210**（ランダム / 内訳は不明）」のように出す。
  確定値に足し込むと、パラメータ別の数字が嘘になる。
- 「優勝したとき」の値なので、**優勝前提**でよいかは決めておく
  （負けた場合も入れるなら、成績の入力が増える）。
- 内部数値の変動は調整ローテ側（`docs/roadmap.md` ②）の話。育成計画では出さなくてよい。

## ② 修行

- **技を覚えるために行くもの。** ついでに能力も少し伸びる（現状は組み込めていない）。
- コスト：寿命-7 / 暦は4週進む（`EV_COST.mc` / `EV_WEEKS.mc`）。
- したがって **「覚える技の数」＝「修行に行く回数」＝ `mc` の合計** になる。
- **修行は5種類あって、上がる能力が違う。** つまり回数だけでは足りず、
  **育成計画に「どの修行か」の入力が要る**。

### 上昇値の扱い

上昇値のデータ自体は用意できる。ただし **通常のトレーニングより扱いが難しい**。

- 通常のトレーニングは **1週ごとにセーブ＆ロードで最高値を出せる**ので、
  いまの育成計算も「重トレは計算に使っている値／軽トレは上がりうる最大値」で成立している。
- 修行は **4週セット**。4週ぶん全部で最大値を出し続けるのは、ほぼ不可能。
- なので **大会と同じ扱い**にする。**ざっくりした合計値**として持ち、
  パラメータ別の確定値には混ぜない。

### 入れるとしたらどうなるか

大会（①）と同じ形にそろえる。

```
set.mc    = 2                    // これまでどおり。寿命-7 / 暦+4週 ×2
set.mTrain = { <種類>: 2 }       // 追加。どの修行に何回行くか。合計は mc と一致
```

- 上昇値は `js/data/growth.js` に修行用の別テーブルとして置く（5種類ぶん）。
- 結果欄に **「修行ぶん +N（ランダム）」を合計値だけ**、大会ぶんと並べて出す。
  トレーニングぶんの確定値とは行を分ける。
- 大会と違って **種類ごとに上がる能力が決まっている**ので、合計値だけでなく
  「ちから寄り +N」くらいまでは出せる。ただし4週ぶんのランダムが乗るので、
  **確定値のような見せ方はしない**（幅か、目安であることが分かる書き方にする）。

**足りないデータ**：5種類の名前と、それぞれで上がる能力・上昇値（送ってもらえる予定）。

## ③ 冒険

- **6月・10月・2月**に、毎年行ける（条件あり）。
- コスト：寿命-2 / 暦は4週進む（`EV_COST.ac` / `EV_WEEKS.ac`）。
- **仕様として組み込む予定はない。** ただし現状の育成計画だと、
  **第◯段階の開始週と週数によっては、そもそも冒険に行ける週に当たらない**。
  （行けない年は、ほかのモンスターを使って週送りすれば合わせられる）

組み込まないと決めているので、やるとしても「行けるかどうかが見えるだけ」で十分。
`weekToDate()` がすでにあるので、**段階の開始時期の表示の横に「この段階に冒険の月が入るか」を
出すだけ**なら、計算を足さずに済む。

## ④ 技

### いまの持ち方

`js/data/monsters.js` は **使い込みで上位技に変わるペアだけ**を持っている。

```js
{ from:"タッチ", to:"はり手", need:30, guts:12, hit:3.8, miss:3.8 }
{ …, milestone:{ need:50, to:"アイショット" } }   // 途中で覚えるもの
```

つまり **「使い込み回数」以外の習得条件を1つも持っていない**し、
**使い込みで覚えない技（最初から持っている技・修行で覚える技）はデータに存在しない**。

### 実際の習得条件

技の習得条件は、使い込み回数だけではない。

- **ステータス**（各パラメータのしきい値）
- **ヨイワル値**

### 一覧はどこにあるか（アプリへの取り込みは見送り）

**全技の一覧と習得条件は @wiki にまとまっている。**
アプリにデータとして取り込むのは **いまは見送り**で、**@wiki を見てもらう**方針。

- リンクは早見タブの「リンク集」にすでに入っている（`js/data/reference-data.js` の `LINKS`）。
  <https://w.atwiki.jp/mf2_matome/pages/158.html>
- なので当面は、技の条件を **アプリが判定することはない**。
  ユーザーが @wiki を見て条件を把握し、その結果として
  「修行に何回行くか」「どのステータスを上げるか」「ヨイ化/ワル化をいつやるか」を
  **自分で育成計画に入れる**、という使い方になる。
- 下の「やりたいこと」以降は、**将来取り込むとしたらこうなる**という案。

### やりたいこと

1. **その種族が覚えうる技を、全部ぶん並べた一覧**を用意する（使い込みのないものも含む）。
2. 技ごとに **習得条件**（ステータス・ヨイワル・使い込み回数）を整理する。
3. それに合わせて **育成計画を立てる**。
   - **覚える技の数だけ、修行に行く**（＝ `mc` が決まる）
   - **覚えたい技の条件から、上げるステータス・上げないステータスが決まる**
   - **ヨイ化 / ワル化のタイミングも、条件から決まる**

つまり「育成計画 → 技」ではなく **「覚える技を選ぶ → 育成計画が決まる」** という向きになる。
これは今の育成計算タブと入力の順序が逆なので、**技を選ぶ画面が計画の手前に要る**。

### データの持ち方（案）

**`js/data/monsters.js` は触らない。** 種族名と技名は保存データのキーなので、
既存の使い込みデータを作り直すと記録が読めなくなる。
**新しいファイル（`js/data/moves.js` など）に技の名簿を足して、名前で突き合わせる**のが安全。

```js
// 種族 → その種族が覚えうる技の全部
"ピクシー": [
  { name:'タッチ',   learn:'init' },                       // 最初から持っている
  { name:'はり手',   learn:'use',   from:'タッチ', need:30 }, // 使い込み（monsters.js と名前で対応）
  { name:'○○○',     learn:'train',                         // 修行で覚える
    req:{ stats:{ int:150 }, moral:[-100,-50] } },          // 条件：かしこさ150以上 / ワル寄り
]
```

- `req.stats` … 満たすべきパラメータのしきい値（複数可）
- `req.moral` … ヨイワルの範囲 `[下限, 上限]`。
  ヨイワルは**初期値から±100までしか動かない**（`moralRange()`）ので、
  **そもそも条件に届かない技がモンスターごとに出る**。ここは判定して弾けるとよい。
- 使い込みぶんは `monsters.js` が持っている値（`need` / `guts` / `hit` / `miss`）が正なので、
  新しい名簿では**重複して持たず、名前で引く**。

### 育成計画へのつなぎ方（案）

```
覚えたい技を選ぶ
  ├→ 技の数            → 修行の回数（mc）→ 寿命 -7×回数 / 暦 +4週×回数
  ├→ req.stats の最大値 → その段階までに上げておくパラメータ（＝重トレ/軽トレの選び方）
  └→ req.moral         → ヨイ化 / ワル化をいつやるか（順番の制約）
```

ヨイワルは条件ごとに逆を向くことがある（ヨイ寄りの技とワル寄りの技を両方覚えたい、など）。
その場合は **「どの技をどの順で取るか」で計画が変わる**ので、
技の選択には**順番（何回目の修行で取るか）**も要る。

### 決めていないこと

- 全部で何種類あるのか（38種ぶん × 技数。使い込みのないものを含めると、いまのデータより大きく増える）
- 条件のデータをどこから、どうやって入れるか（①の派生種400種と同じ「入力が本番」問題）
- 派生種で覚える技が変わるなら、名簿は **種族ごとか派生種ごとか**（`docs/roadmap.md` ① と絡む）
- 技を選ぶ画面をどこに置くか（使い込みタブの隣か、育成計算タブの手前か）
- 条件を満たしているかの判定を、**育成計画の試算結果**でやるのか、実測値でやるのか
